    InferenceX DSV4.1 agentic (request-level pairs)¶

    BLIS binaries these results describe

    • (devel)+9e3c509c8788fe0743605a8f06e0bf5c1c39ac1f, binary sha256 29fb09054a10ee51dc104f491cb09337e0ba527055b85653d281f23230451dff

    DeepSeek-V4.1-Flash on Hopper, vLLM with DSpark speculative decoding, driven by InferenceX's agentic replay (aiperf scenario inferencex-agentx-mvp). BLIS replays the same trace corpus and seed. Measured per-request records come from the runs' GitHub Actions artifacts, bound to the published database rows by recomputing every row with InferenceX's own code.

    Build: 9e3c509c. Every error is 100 * (BLIS / measured - 1): negative means BLIS is faster (lower latency) or, for throughput and interactivity, lower.

    Provenance verdict¶

    Every arm is PARTIAL. The deployment matches field for field (TP, EP, max-num-seqs, capture size, max-num-batched-tokens, gpu-memory-utilization, max-model-len, block size, CUDA graph mode, Engram CPU offload, speculative settings), and the corpus, scenario, seed and window are the run's. These differences remain:

    setting measured run BLIS verdict note
    vLLM image vllm/vllm-openai:nightly-cd10ed6f9f6b37a8ace9cf380007e66fe12ec0c3 kernel engine behaviour v0.31.0 (blis-latency-kernel new.go:2517) MISMATCH (not removable) server log: vLLM 0.29.1rc1.dev128+gcd10ed6f9
    aiperf harness aiperf profile --scenario inferencex-agentx-mvp aiperf release 0.12.0 transcription MISMATCH (not removable) fork differs from release in agentic_replay.py, weka_trace.py, branch_orchestrator.py, replay_dependencies.py; metric formulas unchanged
    trace idle-gap cap --trace-idle-gap-cap-seconds 300 unset (schema refuses) MISMATCH (not removable) inactive at c1 (0 'Per-trace idle cap advanced' lines), active at c>=2
    cache-pressure warmup --warmup-requests-per-lane 10 synthesized only MISMATCH (not removable)
    compilation mode NONE no field (kernel prices CUDA-graph replay) UNSTATED torch.compile disabled in the run (mode NONE); graphs FULL_AND_PIECEWISE
    frontend/runner env Rust frontend launched (server log) not modelled UNSTATED

    Population metrics at concurrency ≥ 2 are confounded by the idle-gap cap: it raises the offered load the run saw beyond what BLIS replays. The comparison that survives every mismatch is the request-level pairing: the same request on both sides, with the same number of requests in flight.

    What would make it EXACT: a run on the vLLM release whose behaviour the kernel prices (v0.31.0), or kernel pricing for the nightly that ran; the aiperf release BLIS transcribes (0.12.0), or a transcription of the fork; blis-schemas Replay support for the per-trace idle-gap cap and per-lane warm-up requests, or a run without them; and the UNSTATED rows stated by the run.
