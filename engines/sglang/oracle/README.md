# Oracle

SGLang v0.5.23's own classes, run on CPU, with only the GPU, the clock, transports, the
environment and the platform replaced (design §7.2, §7.3). The release and commit are
`Upstream` in [`provenance.go`](../provenance.go).

## Environment

SGLang is read from a checkout of the pinned commit, never installed: a runner takes the
checkout as its first argument and puts `<checkout>/python` first on `sys.path`. CI checks out
the commit `provenance.go` names and fails if the checkout is any other
(`.github/actions/oracle-env`).

`oracle/requirements.lock` is the rest of the environment, every package pinned (CPython 3.12,
Linux x86_64, CPU). `oracle/requirements.txt` gives the direct pins it was resolved from and
says what is left out. That is SGLang's CUDA-only kernels and runtimes, and the media packages
the scheduler does not import. torch is the PyTorch CPU wheel of SGLang's pin. `oracle/lock.sh`
writes the same pins with every archive's sha256 into `oracle/requirements-hashed.txt`, and
pip's own release into `oracle/requirements-pip.txt` (X21). Install them with:

```sh
python -m pip install --require-hashes -r oracle/requirements-pip.txt
pip install --require-hashes --no-deps --extra-index-url https://download.pytorch.org/whl/cpu \
  -r oracle/requirements-hashed.txt
python -I oracle/check_lock.py oracle/requirements.lock <(pip freeze)
```

After changing the lock, run `oracle/lock.sh` and commit all three files. CI runs
`python -I oracle/check_lock.py --hashed oracle/requirements.lock oracle/requirements-hashed.txt`
first, and it fails while they disagree; it then installs the pinned uv from
`oracle/requirements-uv.txt`, outside the environment, and runs `oracle/lock.sh --check`. To regenerate the lock, install `oracle/requirements.txt`
in a clean CPython 3.12 environment on Linux x86_64 with the PyTorch CPU index, then run
`pip freeze > oracle/requirements.lock` and keep the header comment.

A CUDA-only module that the scheduler's import or start-up reaches is stubbed by
`oracle/stubs.py` and listed in `oracle/mocks.json`. Any other import of a package left out of the
lock fails. `python -I oracle/run_import.py <sglang checkout>` imports the scheduler module the
runners drive. CI runs it, together with the manifest check
`python -I oracle/check_mocks.py oracle/mocks.json`.

`oracle/peers.json` pins the KV-transfer and KV-store clients SGLang drives (Mooncake, NIXL,
LMCache) and gives the source of each pin. None is in the lock yet, so a scenario that selects one
is refused by name. When a store package enters the lock, it runs as code under test at its pin
(FID-12); `oracle/check_peers.py`, run in CI, fails if the lock pins one at another version.

## The shared checks

`check_lock.py`, `check_mocks.py` and `check_goldens.py` are copies of blis-substrate's
`contracts/harness`, generated by
`go run github.com/inference-sim/blis-substrate/contracts/harness/cmd/harnessfiles`. Never edit
them. `harness.json` configures them for this repository: SGLang's decision modules, the harness
files `check_mocks.py` reads, and the golden directories.

## Tier 2: the scheduler

```sh
ORACLE_MODEL=<config files of Qwen/Qwen2.5-0.5B-Instruct at the revision .github/actions/oracle-env pins> \
ORACLE_MODEL_REVISION=<that revision> ORACLE_LOCKFILE=<pip freeze> HF_HUB_OFFLINE=1 \
  python -I oracle/run_scheduler.py <sglang checkout> oracle/scenarios/<scenario>.json [out.json]
```

`run_scheduler.py` calls SGLang's own entry point, `run_scheduler_process`, in a child process,
as SGLang's launcher does. That entry point publishes the runtime context, builds
`Scheduler(server_args, port_args)` through `Scheduler.__init__`, and runs the event loop that
ServerArgs selects. `harness.py` makes the replacements `mocks.json` lists before SGLang's
scheduler module is imported. These are the model runner's forward pass, sampling, weight loading,
attention backends and CUDA graphs (GPU); the device memory queries (platform); the tokenizer
socket (an outside service) and the scheduler's other sockets (transport); and the clock of every
loaded decision module and observability module. The runner fails if one of those still reads the
real clock after the run, if a receive ends with arrivals undelivered, or if the tree core is not
the Python one. It removes the caller's `SGLANG_*` variables, sets only those it lists, and writes
no trace when a check fails.

The event loops run unmodified. The socket the scheduler reads from the tokenizer starts a step
on its first receive in each loop iteration and yields that step's arrivals. Once every request
has finished, it yields a `ShutdownReq`. SGLang's own `Scheduler.handle_shutdown` then sets
`gracefully_exit`, and the loop returns. The harness writes no scheduler state and copies no loop
body. Every recorded forward pass names the loop on its call stack, and the runner fails unless
that loop is SGLang's own code object, `Scheduler.event_loop_normal` or `event_loop_overlap`.

A trace records, for each loop iteration:

- the requests that arrived;
- each forward pass: its mode, batch size, sequence, extend and prefix lengths, and the allocator's free tokens;
- each output the scheduler sent;

and, once, the pool size SGLang reported at start-up, the tree-cache, tree-core and allocator
classes, the receive settings and the `SGLANG_*` variables the scheduler ran with.

## Traces and goldens

Every runner writes its trace through `traces.py`, which defines the format. A trace is one JSON
object. Its `provenance` block says where the trace came from (FID-2). Every other key is what
SGLang decided, and that is what the Go port is compared on. The block holds these keys and no
others:

| Key | Value |
|---|---|
| `tier` | the oracle tier |
| `sglang_commit` | the checkout's commit, the one `provenance.go` pins |
| `requirements_lock_sha256` | sha256 of `oracle/requirements.lock` |
| `lockfile_sha256` | sha256 of the environment's `pip freeze` |
| `scenario_sha256`, `seed` | the scenario file's sha256, and its seed |
| `mock_version` | `oracle/mocks.json`'s version |
| `model`, `model_revision` | the scenario's model and the revision of its configuration files |
| `python`, `platform` | the interpreter and `<system>-<machine>` |
| `blis_sglang_commit` | this repository's commit, marked `+dirty` if a file the run read differs from it |
| `oracle_inputs` | each `oracle/` file the run read, the scenario included, with its sha256 |

A run that cannot fill a key fails, and writes nothing.

The committed goldens are under `testdata/golden/`. These rules hold them:

- **compare_goldens.py**, in the `oracle` job, runs every scenario. Each golden must equal the fresh
  trace outside its provenance and record the same tier, manifest version, model, lock, scenario
  and seed. A key that one side lacks fails.
- **check_provenance.py**, in `oracle-checks`, is the trace provenance check. It reads files only.
  Every golden must record the commit `provenance.go` pins, the sha256 of the committed lock, the
  current manifest version, and a scenario of this tree, unchanged, with that scenario's seed.
- **check_goldens.py**, in `goldens-reviewed`, fails a commit that changes a golden's decisions
  unless the commit carries a `golden-reviewed: <trace>: <reason>` trailer (FID-3).
- **The runners refuse** to write into a golden directory or golden file of `harness.json`, or under
  any `testdata/golden*`, unless `BLIS_SGLANG_ALLOW_GOLDEN_UPDATE=1`.
- **refresh_provenance.py** needs that flag too.

When the environment changes (a new manifest version, a new lock), `check_provenance.py` fails until
the goldens record it. Push the change, download the `oracle-traces` artifact of its `oracle` job,
then run:

```sh
BLIS_SGLANG_ALLOW_GOLDEN_UPDATE=1 python3 -I oracle/refresh_provenance.py oracle/testdata/golden <artifact dir>
```

That copies each fresh trace's provenance into its golden, and only that. It refuses a golden whose
decisions differ from the fresh trace, or that ran another scenario or seed. Commit the result. A
change that alters decisions instead re-records the golden with the runner, and the commit carries
the trailer.

## Value coverage and the mutation sweep

`value_coverage.py`, in `oracle-checks`, is the value-coverage report (FID-10). It reads every
key of every golden outside its provenance block. A field is named by its path, with `[]` for a list
element and `*` for a key of a map that `value_coverage.json` lists in `maps`. Each field must take
two distinct values somewhere in the scenario set, so that a comparison of it can fail. For a list,
the two values are empty and not empty. A field that takes one value is listed in `held` in
`value_coverage.json`, with one of three kinds:

- `fixed`: the oracle holds it by construction;
- `no_neutral`: its neutral value cannot occur;
- `gap`: no scenario moves it yet. The entry cites the open issue that adds the scenario (X28).

The report fails on a held field that is now covered, and on one that no golden has.
`--report` prints every field with its values.

`mutate.py` is the mutation sweep (T7), run by `.github/workflows/mutation.yml`. It applies one
one-line break at a time to a scratch copy of the tree and runs the suite that must catch it. There
are two kinds of mutant:

- **Listed mutants** are in `mutants.json`. They cover the oracle's own checks (X18). A lane that
  ports a row adds that row's mutants there.
- **Generated mutants.** Every Go file ported from SGLang gets its relational, equality and logical
  operators flipped one at a time. Its package tests must catch each flip.

A survivor fails the sweep, unless `mutants.json` lists it in `known_gaps`, citing the issue, or in
`equivalent`, saying why. A pull request sweeps what it changed: the listed mutants of each changed
file and of each changed test file, and the generated mutants of each changed ported function. The
full sweep runs nightly, on release tags and on demand.

```sh
python3 -I oracle/mutate.py [--changed <base>] [--list] <sglang checkout> <scratch dir>
```
